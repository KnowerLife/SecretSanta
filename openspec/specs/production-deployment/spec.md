# production-deployment Specification

## Purpose

Определяет требования к воспроизводимому production-запуску v69: образы API и SSR-приложения, конфигурация через окружение, применение миграций, проверки готовности и возможность отката.

## Requirements

### Requirement: Образы и оркестрация

Система MUST предоставлять сборку контейнеров для Hono API и SSR-приложения и описание их совместного запуска.

#### Scenario: Локальная сборка

- **WHEN** выполняется сборка по файлам контейнеров v69
- **THEN** создаются два образа, API слушает настроенный порт, а веб-приложение отдаёт SSR-страницы через прокси к API

#### Scenario: Общий запуск

- **WHEN** поднимается compose-стек v69
- **THEN** API и веб-приложение запускаются вместе, имеют общую сеть и постоянный том для базы данных

### Requirement: Конфигурация без секретов в коде

Система MUST получать секреты, пути базы и адрес API из переменных окружения и MUST предоставлять шаблон `.env.example`.

#### Scenario: Отсутствие секретов в репозитории

- **WHEN** проверяется конфигурация production-стека
- **THEN** пароли, ключи VAPID и секрет подписи заданы только через переменные окружения

#### Scenario: Локальный запуск по шаблону

- **WHEN** пользователь копирует `.env.example` в `.env` и задаёт значения
- **THEN** стек запускается без правки исходного кода

### Requirement: Миграции и проверка готовности

Система MUST применять миграции базы при запуске API и отдавать успешный ответ health-эндпоинта только после успешного применения.

#### Scenario: Первый запуск на пустой базе

- **WHEN** контейнер API стартует с пустой базой
- **THEN** схема создаётся автоматически, health-эндпоинт возвращает успешный ответ, а веб-приложение может выполнить запросы

#### Scenario: Ошибка миграции

- **WHEN** применение миграции завершается ошибкой
- **THEN** API не сообщает о готовности и записывает причину в логи

### Requirement: Версионирование и откат

Система MUST использовать версионированные образы и сохранять предыдущую версию для отката.

#### Scenario: Откат релиза

- **WHEN** новая версия ведёт себя ошибочно и выполняется откат
- **THEN** поднимается предыдущая версия образов с той же базой данных, а схема остаётся совместимой

### Requirement: Валидация секретов при запуске

Система MUST проверять `SECRET_SANTA_SECRET` при старте API и воркера и MUST NOT начинать приём запросов с дефолтным, коротким или известным заглушечным значением в production.

#### Scenario: Production с дефолтным секретом

- **WHEN** `NODE_ENV=production`, а `SECRET_SANTA_SECRET` равен `dev-insecure-change-me` или короче 32 символов
- **THEN** процесс завершается с сообщением, объясняющим требование, и не открывает порт

#### Scenario: Локальная разработка

- **WHEN** `NODE_ENV` не равен `production` и секрет не задан
- **THEN** система сохраняет текущий режим разработки и предупреждает в логах об использовании тестового значения

#### Scenario: Перенос токенов v68

- **WHEN** миграция v68 воссоздаёт токены с тем же секретом
- **THEN** она применяет ту же проверку и не создаёт более слабые токены, чем запущенный API

### Requirement: Публикация версионированных образов

Система MUST собирать образы API и web с полным именем registry и публиковать их автоматически по тегу версии, сохраняя предыдущий тег доступным для отката.

#### Scenario: Публикация по тегу

- **WHEN** в репозиторий запушен тег `v*`
- **THEN** workflow собирает оба образа, логируется в registry с секретами репозитория и публикует тег версии и `latest`

#### Scenario: Локальная сборка без registry

- **WHEN** переменные registry не заданы
- **THEN** compose использует локальные имена образов и запускается без доступа к registry

#### Scenario: Сборка без локальных секретов

- **WHEN** сборка образа выполняется в каталоге с `.env` и локальными файлами базы
- **THEN** эти файлы не попадают в контекст сборки и не сохраняются в слоях образа

### Requirement: Откат по тегу

Система MUST позволять вернуть предыдущую версию образов, не изменяя том базы данных и схему в пределах совместимой версии.

#### Scenario: Возврат к предыдущему тегу

- **WHEN** администратор задаёт `V69_IMAGE_TAG` значением предыдущего релиза и перезапускает compose
- **THEN** поднимаются предыдущие образы API и web с тем же томом БД, health-проверка проходит, а текущие сессии остаются действительными
