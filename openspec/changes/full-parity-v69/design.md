# Design

## Context

v69.0.0 уже выпущен и работает на React 19 / Vite 8 / TanStack Start + Router + Query / Mantine 9 и Hono на Node 22. Старый v68 остаётся эталоном: в нём есть локальная игра, демо в один клик, групповые исключения, добавление участников, push и напоминания, интерактивные гиды и подтверждения. Аудит выявил 164 неиспользуемых ключа локализации и более 16 интерактивных элементов, которых нет в v69: раскрытие получателя, прогресс и чеклист, читаемый журнал, шаблоны чата, текст приглашения, подсказки установки, обязательная дата и тема, персональные ссылки быстрой жеребьёвки. Часть возможностей реализована только на уровне API (`groupName`, push-эндпоинты), но не имеет интерфейса; production-деплой и перенос данных отсутствуют. См. `proposal.md` для обоснования и `openspec/specs/` для текущих контрактов.

## Goals / Non-Goals

**Goals:**

- Закрыть функциональный разрыв с v68, сохранив новую архитектуру и не возвращая JPG-ассеты или hash-роутинг.
- Обеспечить единый источник игровой логики для серверного и локального режимов.
- Сделать перенос данных v68 воспроизводимым и проверяемым.
- Дать воспроизводимый production-запуск и проверки в CI.

**Non-Goals:**

- Изменение уже зафиксированных публичных контрактов приватности `assignment`.
- Возврат старого кода `src/*.js` в Basic-приложение.
- Полноценная многопроцессная синхронизация через Redis: SSE остаётся in-memory.
- Публикация релиза, тега и слив в `main` без отдельного разрешения.

## Decisions

### Демо и локальный режим

Демо создаётся серверным эндпоинтом с предзаполненными участниками и проведённой жеребьёвкой, затем открывает обычный маршрут `/room/<code>` с меткой демо. Альтернатива — локальная демо-игра целиком в браузере — отклонена: она дублировала бы модель данных и сделала бы демо непроверяемым через API.

Локальная игра при недоступном API реализуется адаптером с тем же интерфейсом, что и HTTP-клиент: запросы читают и пишут версионированное состояние в `localStorage`, а жеребьёвка использует `@secret-santa/shared`. После восстановления сети локальные изменения не перезаписывают сервер молча — пользователю предлагается явный выбор. Это сохраняет офлайн-игру v68 без возврата к старым ES-модулям.

### Группы и участники

Схема v69 уже хранит `group_name` в таблице исключений. Добавляется один атомарный эндпоинт для создания группы и эндпоинты добавления/удаления участника с проверкой роли организатора. Альтернатива — отправлять N одиночных запросов из UI — отклонена из-за частично применённых изменений при ошибке. Удаление участника аннулирует его сессии и делает текущий забег недействительным.

### Push без дополнительных зависимостей

VAPID-токен подписывается через `node:crypto` (ES256), а push-сообщение отправляется без зашифрованного payload. Service worker показывает уведомление по локально сохранённым метаданным комнаты. Такой подход исключает утечку имён получателей и содержимого чата и не добавляет тяжёлую библиотеку. Альтернатива — `web-push` с шифрованием payload — отклонена: избыточна для напоминаний и усложняет аудит приватности. Воркер периодически сканирует комнаты и таблицу задач, отправляя напоминания не чаще одного раза на окно.

### Гиды и обратная связь

Интерактивные гиды собираются из уже подготовленных ключей локализации в FSD-слоях; состояние шагов хранится в провайдере настроек. Для уведомлений и подтверждений используются `Mantine Notifications` и `Mantine Modal` вместо копирования старого `feedback.js`. Разрушительные действия требуют подтверждения, а фокус возвращается к инициатору.

### Дашборд и совместимость API

Раскрытие получателя остаётся явным действием: сервер по-прежнему возвращает только назначение текущего участника, а кнопка лишь меняет локальное представление. Прогресс, чеклист и читаемый журнал вычисляются из уже загруженных `RoomView` и `activity` на клиенте, без новых эндпоинтов. Шаблоны чата и текст приглашения собираются из существующих ключей локализации.

API-совместимость восстанавливается точечно: upper-case коды, `404` для неизвестной комнаты, точный SSE-курсор по существующему событию, единые имена событий и ограничение частоты запросов. Старые токены не совместимы с форматом v69, поэтому миграция перевыпускает их и сохраняет соответствие, чтобы старые ссылки продолжали работать. Альтернатива — поддержка обоих форматов навсегда — отклонена из-за увеличения поверхности атаки.

### Перенос данных и деплой

Миграция v68→v69 выполняется отдельным TypeScript-скриптом на `node:sqlite` с режимом dry-run, контролем счётчиков и контрольной суммой исходного файла. Исходная база только читается. Для production добавляются `Dockerfile` API и web, compose с постоянным томом, `.env.example` и healthcheck. API запускает миграции при старте; образы версионируются.

## Risks / Trade-offs

- [Локальный режим может расходиться с серверным состоянием] → явный выбор пользователя при восстановлении сети, версионированный ключ хранилища и тесты на расхождения.
- [VAPID-ключи не заданы в окружении] → push отключается с понятным сообщением, остальной функционал не страдает.
- [Схемы v68 и v69 различаются] → миграция с проверкой счётчиков и возможностью отката, обязательный dry-run перед применением.
- [Браузерные проверки Lighthouse чувствительны к нагрузке] → фиксировать performance отдельно от доступности, не блокировать релиз флуктуациями.
- [Force-push в истории раннего релиза изменил SHA] → все ветки и тег уже обновлены; новые работы ведутся от актуального `develop`.

## Migration Plan

1. Открыть feature-ветку от `develop` и реализовать изменения по группам задач, сохраняя зелёные `npm run typecheck`, `npm test`, `npm run build`.
2. Добавить эндпоинты и воркер API, затем адаптеры и интерфейс веба; проверять каждый слой unit-тестами.
3. Подготовить скрипт миграции, прогнать его на копии базы v68 и зафиксировать отчёт.
4. Добавить контейнеры, compose, healthcheck и CI-прогон браузерных сценариев v69.
5. После зелёного CI и явного разрешения владельца — отдельный релиз `v69.1.0` с тегом и сливом в `main`.

## Open Questions

Нет: выбор между серверным демо, локальным режимом и push без payload зафиксирован выше и не требует изменения спеки.
