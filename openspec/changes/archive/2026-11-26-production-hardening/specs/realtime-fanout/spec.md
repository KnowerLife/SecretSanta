# Spec Delta

## Purpose

Определяет доставку событий комнаты между несколькими процессами API: брокер события, устойчивый курсор, точный replay и очистка журнала без нарушения приватности назначений.

## ADDED Requirements

### Requirement: Доставка между процессами

Система MUST доставлять события комнаты всем подключённым клиентам независимо от того, какой процесс API обработал mutation. При заданном `REDIS_URL` система MUST использоватьвнешний Pub/Sub брокер; без него система MAY работать в режиме одного процесса с in-memory шиной.

#### Scenario: Событие из другой реплики

- **WHEN** событие создано первым процессом API, а клиент подключён ко второму процессу с общим `REDIS_URL`
- **THEN** второй процесс получает событие через брокера и отправляет его клиенту без повторного чтения базы на каждое событие

#### Scenario: Недоступный брокер

- **WHEN** `REDIS_URL` задан, но брокер недоступен при старте
- **THEN** система логирует причину и не сообщает о готовности multi-instance режима, не перенаправляет клиентские токены и не раскрывает данные комнаты

### Requirement: Глобально монотонный курсор

Система MUST использовать в кадре `id` значение, монотонное для всей базы и сохраняемое между перезапусками; система MUST принимать его в заголовке `Last-Event-ID` и возвращать только более поздние события комнаты.

#### Scenario: Продолжение после перезапуска

- **WHEN** клиент переподключается с `Last-Event-ID`, выданным до перезапуска процесса
- **THEN** сервер возвращает события с идентификатором больше сохранённого в порядке возрастания и не повторяет уже доставленные

#### Scenario: Неизвестный курсор

- **WHEN** клиент передаёт курсор, которого нет в журнале комнаты
- **THEN** сервер отправляет доступные события с начала окна replay и кадр `connected` без `id`, не раскрывая события другой комнаты

### Requirement: Replay без гонки и дубликатов

Система MUST создавать подписку на шину до чтения replay-лога и MUST отсекать события, уже отправленные во время replay.

#### Scenario: Событие между replay и подпиской

- **WHEN** новое событие публикуется в момент чтения replay-лога
- **THEN** клиент получает его один раз, после полного replay, и кадр `connected` остаётся без идентификатора

#### Scenario: Приватность кадров

- **WHEN** формируется кадр события комнаты для SSE
- **THEN** он содержит только публичные поля события и MUST NOT содержать имя получателя, полный список пар или содержимое чата

### Requirement: Жизненный цикл соединения и журнала

Система MUST отписываться от шины и останавливать heartbeat при закрытии потока или отмене запроса. Система MUST ограничивать размер replay и очищать старые записи журнала, не удаляя события внутри настраиваемого окна.

#### Scenario: Обрыв соединения

- **WHEN** клиент закрывает `EventSource` или запрос отменён
- **THEN** сервер снимает подписку, останавливает `ping` и не продолжает буферизовать события для этого клиента

#### Scenario: Очистка старых событий

- **WHEN** выполняется фоновая очистка `room_events`
- **THEN** удаляются только записи старше настроенного окна, а клиент с активным курсором внутри окна продолжает получать replay без пропусков
