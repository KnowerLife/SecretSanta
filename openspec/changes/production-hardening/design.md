# Design

## Context

`v69.1.1` уже имеет рабочие образы API/web, compose с healthcheck и воркером, миграцию v68→v69 и браузерные проверки. При этом `RoomEventBus` в `apps/api/src/events.ts` хранит слушателей в `Map` одного процесса, `emit()` в `app.ts` генерирует курсор из локального счётчика, а `room_events` в SQLite используется только для replay. Секрет подписи читается один раз с дефолтом `dev-insecure-change-me`, `/api/health` и `/api/push/config` определяют готовность push по наличию переменных, а не через `pushEnabled()`. Образы называются `secret-santa-api:v69.1.1` без registry, и в репозитории нет workflow публикации. Текущее состояние зафиксировано в `docs/PARITY_v69.md` и отчёте разведки по коду.

## Goals / Non-Goals

**Goals:**

- Обеспечить доставку событий комнаты между экземплярами API без изменения клиентского контракта SSE.
- Сделать курсор события устойчивым к перезапуску и нескольким процессам, сохранив точный replay.
- Отказывать в запуске production с заведомо слабым секретом и несовместимыми VAPID-ключами.
- Дать воспроизводимую публикацию версионированных образов и откат по предыдущему тегу.

**Non-Goals:**

- Переход на PostgreSQL и полноценная замена SQLite: replay-лог остаётся в текущей базе.
- Изменение формата токенов и приватности назначений получателя.
- Переписывание v68, `backend/prod_stack/` и legacy-тестов.
- Выпуск тега или слив в `main` без отдельного разрешения владельца.

## Decisions

### Шина событий

Вместо прямого `roomEvents.publish()` вводится интерфейс брокера с двумя реализациями: in-memory для локальной разработки и Redis Pub/Sub при заданном `REDIS_URL`. Канал называется по внутреннему `roomId`; сообщение содержит только уже существующий публичный payload события, без имён получателей и содержимого чата. Redis — необязателен для одного процесса, но для нескольких реплик `REDIS_URL` обязателен и это проверяется документацией и тестом конфигурации. Альтернатива — polling таблицы `room_events` каждые N миллисекунд — отклонена из-за задержки и нагрузки на базу.

### Курсор и replay

Идентификатор SSE-кадра берётся из `rowid` вставленной записи `room_events`; он же используется в `Last-Event-ID`. Это устраняет локальный счётчик `Date.now()*1000 + counter`, который не уникален между процессами. Подписка на шину создаётся до чтения replay-лога; найденные позже события дедуплицируются по идентификатору, чтобы закрыть текущую гонку между replay и `subscribe()`. Кадр `connected` по-прежнему отправляется без `id` после replay. Для старых баз, где в старых событиях ID не совпадает с `rowid`, миграция не переписывает историю: обработчик курсора принимает число и сравнивает его с `CAST(id AS INTEGER)`, как и сейчас.

### Надёжность и очистка

Сервер отписывается от шины и останавливает `ping` не только в `cancel()`, но и при закрытии потока/отмене запроса. Добавляетсяпредопределённый лимит replay (200 кадров, как сейчас) и фоновая очистка `room_events` по возрасту с настраиваемым окном; очистка не удаляет события, созданные позже границы, чтобы не сломать активные курсоры. Backpressure обрабатывается отключением медленного клиента, а не бесконечной очередь в памяти.

### Секрет подписи

Проверка выносится в отдельный модуль конфигурации и вызывается при старте API и воркера: в production дефолтное значение, длина менее 32 символов и известные заглушки запрещены. Значение читается один раз, поэтому смена секрета означает инвалидацию всех токенов; процедура ротации описывается в README. Модуль миграции токенов переиспользует ту же проверку, чтобы исключить расхождение между основным API и переносом v68.

### VAPID

`pushEnabled()` остаётся единственным источником истины: он проверяет пару ключей, а не только ENV-заглушки. `/api/health`, `/api/push/config` и ответ `/api/push/subscribe` используют этот результат. Для проверки пары публичный ключ выводится из приватного и сравнивается с заданным; несовпадение означает `enabled: false` и предупреждение в логах. Воркер по-прежнему оставляет задачи в очереди, если доставка недоступна. Документируются команды генерации пары P-256 и шаги ротации без раскрытия приватного ключа.

### Образы и публикация

Имена образов собираются из `V69_IMAGE_REGISTRY` и `V69_IMAGE_NAMESPACE` с дефолтом на локальные имена, поэтому текущий `docker compose up` не ломается. Workflow публикации запускается по тегу `v*` и по ручному `workflow_dispatch`, использует официальные `docker/login-action` и `docker/build-push-action` с секретами registry, публикует тег версии и `latest` для web/API. `.dockerignore` исключает `.git`, `.env`, локальные базы и артефакты сборки. Откат — переключение `V69_IMAGE_TAG` на предыдущий тег при том же томе БД; обратная совместимость схемы уже является частью `production-deployment`.

## Risks / Trade-offs

- [Redis недоступен] → API продолжает работать в in-memory режиме с предупреждением; для multi-instance это считать ошибкой конфигурации и проверять тестом.
- [Смена курсора на `rowid` меняет формат `id`] → клиент уже передаёт `Last-Event-ID` как строку и не разбирает его; контракт тестов replay сохраняется.
- [Очистка `room_events` может выбросить нужное событие] → удалять только записи старше настраиваемого окна и только с `rowid` меньше границы.
- [Проверка пары VAPID отклонит рабочие ключи] → оставить fallback на `enabled: false` без падения API; добавить тест на невалидную пару.
- [Публикация в registry потребует секретов] → шаги `docker/login` выполняются только для тегов и не влияют на локальную разработку; секреты не попадают в образ.

## Migration Plan

1. Открыть feature-ветку от `develop`, реализовать адаптер шины и тесты multi-instance, сохранив зелёные unit-тесты API.
2. Перевести SSE на курсор из базы и устранить гонку replay/подписки; прогнать `api.sse_replay` и браузерные проверки.
3. Добавить валидацию секретов и VAPID, обновить health/contract-тесты и документацию по ключам.
4. Обновить compose, `.env.example`, добавить `.dockerignore` и workflow публикации; проверить сборку локально.
5. Обновить README, `docs/PARITY_v69.md` и `apps/api/WORKER.md`; прогнать полный набор проверок включая Lighthouse.
6. После зелёного CI и явного разрешения владельца — отдельный релиз и тег по правилам `docs/RELEASES.md`.
