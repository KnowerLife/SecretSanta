# Design

## Context

Текущая v68 — рабочий продукт: 18 ES-модулей frontend, Python-бэкенд на stdlib + SQLite, 19 браузерных проверок, 12 Lighthouse-прогонов со score 1.0 и полностью русский README. Его нужно сохранить как эталон поведения. См. `proposal.md` для мотивации и `specs/` для требуемого поведения. Ограничения: Node 22.22+, npm 10, Vite 8.3.8 требует Start 1.169+, OpenSpec 2.2.0; исходные файлы v68 не должны ломаться до релиза v69.

## Goals / Non-Goals

**Goals:**

- Типизировать весь код приложения и API на TypeScript без `any` в публичных контрактах.
- Обеспечить SSR для публичных страниц и прямых переходов в комнату.
- Перенести поведение v68 в новый стек с измеримым паритетом через тесты.
- Сделать релизы воспроизводимыми: Gitflow-ветки, теги, CHANGELOG, OpenSpec-архив.

**Non-Goals:**

- Удаление или переписывание working v68 до момента выпуска v69.
- Переход на PostgreSQL/Redis в этом change: каркас `backend/prod_stack/` остаётся scaffold.
- Полная замена Python-бэкенда на production-инфраструктуру: новый Hono API пока работает с отдельной SQLite-БД.
- Автоматическая миграция данных между старой и новой БД без явного сценария.

## Decisions

### 1. Параллельное развитие в монорепозитории

Новый код живёт в `apps/web`, `apps/api`, `packages/shared`, `packages/art`; старые файлы остаются на месте. Корневой `package.json` расширяется до npm workspaces, сохраняя скрипты браузерных проверок v68.

Альтернатива: big-bang замена — отклонена, так как теряет рабочий эталон и усложняет откат.

### 2. TanStack Start + Vite 8 на Rolldown

Используем `@tanstack/react-start/plugin/vite` с строгим порядком плагинов: `tanstackStart()` перед `viteReact()`. SSR-данные идут через server functions и route loaders, клиентское состояние — через TanStack Query. Прямые URL вида `/room/:code` заменяют hash-роутинг.

Альтернатива: отдельный Express SSR-сервер — отклонена из-за дублирования инфраструктуры и более сложной гидратации.

### 3. Mantine 9 как дизайн-система

Стили подключаются через `?url` в `links` корневого роута, `ColorSchemeScript` и `mantineHtmlProps` обеспечивают SSR-безопасность. Три темы v68 отображаются на Mantine `MantineProvider`: `winter` и `cozy` — light-палитры с разными primary, `midnight` — dark. Токены цветов дублируются в CSS-переменных, чтобы SVG-сцены перекрашивались вместе с темой.

Альтернатива: сохранение `styles.css` — отклонена: 2272 строки кастомных стилей не типизированы и не дают единой сетки компонентов.

### 4. FSD как архитектурный стиль frontend

Слои: `app` (провайдеры, роутер, темы), `pages` (тонкие страницы), `widgets` (композитные блоки дашборда), `features` (создание комнаты, вход, быстрая жеребьёвка, чат), `entities` (room, member, draw), `shared` (UI-примитивы, API-клиент, i18n, утилиты). Импорты идут только вниз по слоям; файлы `src/routes/` содержат только объявления TanStack Router и delegation в `pages`.

Альтернатива: плоская папка по компонентам — отклонена из-за отсутствия явных границ при росте числа фич.

### 5. Hono + TypeScript + `node:sqlite` для API

Новый API изолирован в `apps/api`. Схема БД создаётся отдельными SQL-миграциями в `apps/api/migrations`; файл БД не совпадает с `backend/data/app.db`, чтобы исключить случайную порчу данных v68. Контракты (`/api/health`, `/api/rooms`, `/api/rooms/:code/*`) проверяются zod-схемами из `packages/shared`. Приватность назначения и organizer-only доступ к activity переносятся без ослабления.

Альтернатива: вызов Python-бэкенда из нового UI — отклонена: оставляет два стека и не решает задачу TypeScript-бэкенда.

### 6. Векторная графика как код

`packages/art` содержит каталог из 36 сцен, палитры трёх тем и чистую функцию `renderSceneSvg(id, theme)`. Детерминированный PRNG по идентификатору сцены даёт стабильный результат; генератор записывает 36 standalone SVG в `apps/web/public/art`. В React сцены рендерятся инлайн, чтобы CSS-переменные темы влияли на цвета.

Альтернатива: конвертация JPG в SVG-контейнеры — отклонена: не даёт настоящей векторности и выигрыша в размере.

### 7. OpenSpec + Gitflow как процесс

Каждый значимый change создаётся через `openspec new change`, проходит `openspec validate --strict` и ведётся в `feature/*` от `develop`. После завершения задач change архивируется в `openspec/changes/archive`, а код выходит через `release/v69.0.0` с тегом. Main обновляется только релизными и hotfix-ветками.

Альтернатива: trunk-based development — отклонена пользователем: нужны явные релизы.

## Risks / Trade-offs

- `node:sqlite` помечен как experimental в Node 22 → изолировать работу с БД в одном модуле, зафиксировать минимальную версию Node и подготовить замену на `better-sqlite3` без изменения контрактов API.
- Vite 8/Rolldown и Start-плагин — новые majors → зафиксировать версии в lockfile и проверять `vite build` в CI на каждом PR.
- Паритет функций не достигнут сразу → держать v68 как отдельную точку входа и не переключать деплой до прохождения всех 19 браузерных проверок на v69.
- Две SQLite-БД → данных между ними нет автосинхронизации; добавить явный экспорт/импорт и документировать перед cutover.
- Инлайн-SVG может увеличить HTML → мемоизировать рендер и лениво монтировать сцены вне первого экрана.
- Mantine SSR может потерять порядок стилей → добавить проверку, что `mantineCoreStyles` первый в массиве `links`.

## Migration Plan

1. Зафиксировать процесс: `develop`, feature-ветка, OpenSpec-change, Gitflow-документация, CI для нового стека.
2. Поднять каркас: workspaces, tsconfig, зависимости, базовый `apps/web` и `apps/api`, зелёный typecheck.
3. Перенести общие контракты: i18n, типы домена, алгоритм жеребьёвки, SVG-каталог с тестами.
4. Реализовать вертикальный срез: главная → создание → вход → быстрая жеребьёвка → дашборд комнаты.
5. Достичь паритета: чат, SSE, приглашения, сессии, профиль, activity, PWA/offline, RU/EN, три темы.
6. Создать `release/v69.0.0`, прогнать полный набор проверок, обновить CHANGELOG и README, поставить тег `v69.0.0`, слив в `main`.
7. Архивировать OpenSpec-change и объявить v69 основным входом в приложение.

## Open Questions

- Куда деплоить SSR-приложение: длинный Node-процесс или serverless-платформа — решается перед релизом и не меняет контракты спецификаций.
- Нужен ли PostgreSQL в релизе v69 — текущий change остаётся на SQLite, переход обсуждается отдельным change.
- Какой почтовый провайдер использовать для напоминаний — выбран stdout-fallback в воркере до выбора провайдера.
