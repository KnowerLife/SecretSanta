## Контракты API v69

- Коды комнат нормализуются в верхний регистр; неизвестная комната возвращает `404 room_not_found` до проверки токена.
- SSE: приоритет заголовка `Last-Event-ID`, валидация курсора по существующему событию, реплей до 200 событий, кадр `connected` без `id` и после реплея, поля `roomCode` / `seq` / `eventDbId`.
- Единые имена событий: `room.drawn`, `room.gift_status`, `profile.note` в профиле участника.
- Ограничение частоты: 30 запросов/мин на IP для `POST /api/rooms`, `/api/rooms/join`, `/api/rooms/:code/invites`, `/api/rooms/:code/sessions/revoke`.
- Push: `/api/push/config` требует оба VAPID-ключа; `/api/push/subscribe` резолвит `roomCode` в id комнаты и сохраняет `keys.p256dh` / `keys.auth`; `/api/rooms/:code/push/test` возвращает `503 push_not_configured` без VAPID.
- Legacy-токены v68 продолжают работать через таблицу `legacy_token_map` и `resolveLegacyToken()`.

## Перенос данных

`npm run migrate:v68 [-- --dry-run|--source PATH|--target PATH]`:

- источник `backend/data/app.db` открывается `readOnly`, контрольная сумма SHA-256 сверяется до и после;
- целевая БД — отдельный `SECRET_SANTA_V69_DB_PATH`, все записи в одной транзакции;
- счётчики по 13 таблицам сверяются, при расхождении транзакция откатывается и команда завершается ненулевым кодом;
- токены приглашений, участников и сессий перевыпускаются с сохранением соответствия старых raw-токенов;
- события перенумеруются в монотонные числовые id, типы приводятся к v69;
- повторный запуск не дублирует строки.

Контрольные счётчики на реальной копии v68: 65 комнат, 222 участника, 65 приглашений, 220 сессий, 3 исключения, 49 забегов, 190 назначений, 5 вишлистов, 46 сообщений, 360 событий, 441 запись в карте токенов.

## Откат v69

Откат производится на том же хосте, тем же файлом `docker-compose.v69.yml` и с тем же томом `v69_api_data`:

1. Задать в `.env` или окружении деплоя предыдущий рабочий `V69_IMAGE_TAG` (например, `v69.1.1`).
2. Если образы публикуются в GHCR, задать те же `V69_IMAGE_REGISTRY` и `V69_IMAGE_NAMESPACE`, что и при публикации; для локальных образов оставить их пустыми.
3. Не удалять том `v69_api_data` (`docker compose down -v` недопустим): API и воркер должны видеть ту же БД по пути `/app/apps/api/data`.
4. Проверить совместимость схемы с предыдущим тегом: миграции из `apps/api/migrations` и состояние `schema_migrations` должны соответствовать образу, к которому выполняется откат. При несовместимости сначала восстановить БД из резервной копии, сделанной до обновления; не применять миграции нового тега после отката.
5. Выполнить `docker compose -f docker-compose.v69.yml pull api web` и `docker compose -f docker-compose.v69.yml up -d --no-build --force-recreate`.
6. Проверить `GET /api/health` напрямую на `$PORT` (по умолчанию `8787`) и через web на `3000`, затем убедиться, что воркер продолжает обрабатывать `notification_jobs`.

Фактический прогон публикации и отката в тестовом пространстве имён registry фиксируется отдельно в чек-листе 4.3; до его выполнения шаги выше считаются процедурой, а не подтверждённым результатом.

## Известные ограничения

- SSE-шина использует Redis, когда задан `REDIS_URL` (в compose он включается автоматически); без брокера остаётся in-memory режим одного процесса. Несколько реплик API без общего Redis не гарантируют доставку событий между процессами.
- `backend/prod_stack/` остаётся каркасом; рабочий production-стенд v69 поднимается через `docker-compose.v69.yml`.
- В production (`NODE_ENV=production` в образах) API, воркер и миграция отклоняют `SECRET_SANTA_SECRET` короче 32 символов, заглушки и отсутствие секрета до открытия порта. Локальная разработка без `NODE_ENV` сохраняет прежнее dev-значение.
- Смена `SECRET_SANTA_SECRET` инвалидирует текущие сессии — это ожидаемое поведение, которое нужно учитывать при ротации.
- VAPID считается включённым только для согласованной пары P-256 и корректного `VAPID_SUBJECT`; несовпадение ключей или заглушки сообщают `enabled: false` во всех трёх эндпоинтах.
- Публикация образов в GHCR добавлена в `.github/workflows/publish-images.yml`; фактический прогон по тегу `v*` и откат на предыдущий образ проверяются отдельно (чек-лист 4.3).
- `npm audit` не показывает уязвимостей: `postcss` обновлён до 8.5.33.
- Переключение на v69 требует миграции данных и VAPID-ключей; старые ссылки работают только после `npm run migrate:v68`.
